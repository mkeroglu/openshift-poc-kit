# 16 — OADP (Velero) Backup/Restore Demo Guide — on ODF S3

> 🇹🇷 [Türkçe](README.tr.md) · [← 15 — ODF Performance Test](../15-odf-performance-test/README.md) · [POC flow](../../README.md) · [17 — OpenShift Virtualization →](../../E-virtualization/17-virtualization/README.md)

This document shows how a namespace is deleted completely and **restored from a backup** with **OADP (OpenShift API for Data Protection / Velero)**. For storage (as in the [12 — Logging](../12-logging/README.md) guide), the **ODF (Ceph RGW, S3-compatible)** already installed on the cluster is used. Every step was **tested end to end on a lab cluster** (OpenShift 4.22, OADP 1.6): the `poc-oadp-demo` namespace was backed up with its content (Deployment, ConfigMap, Secret, Service **and a PVC with data written to it**), the namespace was deleted completely, then fully restored from the backup, and the MD5 checksums of the files on the PVC came out identical.

Scenario order:

1. Prerequisite check (OADP operator, ODF S3 backend)
2. Preparing the S3 bucket + credentials (ODF/Ceph RGW)
3. Creating the `DataProtectionApplication` (DPA)
4. Creating a test namespace and resources in it
5. Taking a backup
6. Deleting the namespace (disaster simulation)
7. Restoring and verifying (actual test output)
8. Known warnings (harmless, seen in the live test)
9. Cleanup

---

## 2. S3 Bucket + Credentials (ODF/Ceph RGW)

```yaml
# oadp-bucket-obc.yaml
apiVersion: objectbucket.io/v1alpha1
kind: ObjectBucketClaim
metadata:
  name: oadp-bucket-odf
  namespace: openshift-adp
spec:
  generateBucketName: oadp-bucket-odf
  storageClassName: ocs-storagecluster-ceph-rgw
```

```bash
oc apply -f oadp-bucket-obc.yaml
oc get obc oadp-bucket-odf -n openshift-adp
```

✅ **Actual output:** `PHASE: Bound` (within seconds).

Create a secret in the **AWS credentials INI format** Velero expects:

```bash
ACCESS_KEY=$(oc get secret oadp-bucket-odf -n openshift-adp -o jsonpath='{.data.AWS_ACCESS_KEY_ID}' | base64 -d)
SECRET_KEY=$(oc get secret oadp-bucket-odf -n openshift-adp -o jsonpath='{.data.AWS_SECRET_ACCESS_KEY}' | base64 -d)

cat > cloud-credentials <<EOF
[default]
aws_access_key_id=${ACCESS_KEY}
aws_secret_access_key=${SECRET_KEY}
EOF

oc create secret generic cloud-credentials -n openshift-adp --from-file=cloud=cloud-credentials
```

> **Note:** the key name inside the secret must be **`cloud`** — the DPA's `credential.key` field references it.

## 3. DataProtectionApplication (DPA)

```yaml
# dpa.yaml
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa-odf
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
        - csi        # to back up PVCs with CSI snapshots (section 5.1)
        - kubevirt   # to back up VMs (17 — Virtualization); not needed without VMs
    nodeAgent:
      enable: false          # PV file-level (kopia/restic) backup off — see section 8
      uploaderType: kopia     # required even with enable:false (CRD validation)
  backupLocations:
    - velero:
        provider: aws
        default: true
        credential:
          name: cloud-credentials
          key: cloud
        objectStorage:
          bucket: REPLACE_ME_BUCKET_NAME   # the real bucket name generated by the OBC in section 2
          prefix: velero
        config:
          region: us-east-1
          s3Url: http://rook-ceph-rgw-ocs-storagecluster-cephobjectstore.openshift-storage.svc:80
          s3ForcePathStyle: "true"
```

```bash
BUCKET=$(oc get cm oadp-bucket-odf -n openshift-adp -o jsonpath='{.data.BUCKET_NAME}')
sed "s/REPLACE_ME_BUCKET_NAME/${BUCKET}/" dpa.yaml | oc apply -f -

oc get backupstoragelocation -n openshift-adp
oc get pods -n openshift-adp
```

✅ **Actual output:** `backupstoragelocation dpa-odf-1` → `PHASE: Available`, `DEFAULT: true`; the `velero-xxxxx` pod is `1/1 Running`.

> **Note (as in the [12 — Logging](../12-logging/README.md) guide):** the RGW endpoint is given over **HTTP (port 80)**, not HTTPS — the traffic is cluster-internal (ClusterIP), so the POC avoids certificate/CA complexity. In production prefer HTTPS with a CA bundle.

## 5. Taking a Backup

```yaml
# backup.yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: poc-oadp-demo-backup
  namespace: openshift-adp
spec:
  includedNamespaces:
    - poc-oadp-demo
  storageLocation: dpa-odf-1
  ttl: 720h0m0s
```

```bash
oc apply -f backup.yaml
oc get backup.velero.io poc-oadp-demo-backup -n openshift-adp -o jsonpath='{.status}'
```

> **Watch out:** on this cluster `oc get backup` (without the full resource name) can collide with **`backups.postgresql.cnpg.noobaa.io`** (the CloudNativePG operator's resource type) and query the wrong resource — a short-name collision. Always use **`oc get backup.velero.io`**.

✅ **Actual output:**

```json
{"completionTimestamp":"...","phase":"Completed","progress":{"itemsBackedUp":58,"totalItems":58},...}
```

### 5.1 Backing up together with PVC data (CSI snapshot)

For applications with persistent disks, add `demo-pvc.yaml` (a 1Gi PVC + `data-app` writing to it) and write data to the PVC:

```bash
oc apply -f demo-pvc.yaml
P=$(oc get pod -n poc-oadp-demo -l app=data-app -o jsonpath='{.items[0].metadata.name}')
oc exec $P -n poc-oadp-demo -- /bin/sh -c 'echo "persistent-data $(date -u +%FT%TZ)" > /data/critical.txt'
oc exec $P -n poc-oadp-demo -- dd if=/dev/urandom of=/data/random.bin bs=1M count=20
oc exec $P -n poc-oadp-demo -- md5sum /data/critical.txt /data/random.bin
```

The backup is taken with `backup-with-volumes.yaml` instead of `backup.yaml`: it has `snapshotVolumes: true` and an annotation that says which VolumeSnapshotClass to use (the DPA needs the `csi` plugin).

```bash
oc apply -f backup-with-volumes.yaml
oc get backups.velero.io poc-oadp-demo-backup -n openshift-adp \
  -o jsonpath='{.status.phase} {.status.progress.itemsBackedUp}/{.status.progress.totalItems} csi={.status.csiVolumeSnapshotsCompleted}/{.status.csiVolumeSnapshotsAttempted}'
```

✅ **Actual output:** `Completed 75/75 csi=1/1` in **22 s**, no errors/warnings.

> Velero normally looks for a VolumeSnapshotClass labeled `velero.io/csi-volumesnapshot-class=true`. If there is no such label and you don't want to change a shared VolumeSnapshotClass, use the annotation method (`velero.io/csi-volumesnapshot-class_<driver>: <class>`).

> **Scope:** CSI snapshots are kept inside Ceph; only the Kubernetes objects are written to S3. This is enough for restoring into the same cluster; for losing Ceph or moving to another cluster you need `nodeAgent.enable: true` in the DPA and `snapshotMoveData: true` (Data Mover) in the Backup.

## 7. Restore and Verification (actual test output)

```yaml
# restore.yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: poc-oadp-demo-restore
  namespace: openshift-adp
spec:
  backupName: poc-oadp-demo-backup
```

```bash
oc apply -f restore.yaml
oc get restore.velero.io poc-oadp-demo-restore -n openshift-adp -o jsonpath='{.status}'
```

✅ **Actual output:**

```json
{"completionTimestamp":"...","phase":"Completed","progress":{"itemsRestored":44,"totalItems":44},"warnings":10}
```

(In the second test round with the PVC: `Completed` in **38 s**, `49/49`, 12 warnings.)

**Confirm that the resources and data really came back:**

```bash
oc get deployment,cm,secret,svc -n poc-oadp-demo
oc get cm demo-config -n poc-oadp-demo -o jsonpath='{.data}'
oc get secret demo-secret -n poc-oadp-demo -o jsonpath='{.data.password}' | base64 -d
```

✅ **Actual output:**

```
deployment.apps/demo-app   2/2 READY   (went to Running without any further intervention)

{"created-at":"2026-08-12","greeting":"hello-oadp-restore-test"}   <-- ConfigMap data came back exactly

s3cr3t-poc-oadp-demo   <-- Secret content came back exactly
```

**Verifying the PVC data:**

```bash
P=$(oc get pod -n poc-oadp-demo -l app=data-app -o jsonpath='{.items[0].metadata.name}')
oc exec $P -n poc-oadp-demo -- md5sum /data/critical.txt /data/random.bin
```

✅ **Actual output:** MD5s before the backup and after the restore are identical (`71a1aad6...  critical.txt`, `f3910388...  random.bin`); the content of the text file is `persistent-data 2026-10-05T23:07:57Z`. The PVC was recreated from the CSI snapshot, and `data-app` attached to it and started on its own.

**Result: the namespace, the Deployment (with its replicas), ConfigMap, Secret and PVC data — all restored exactly, with their content.**

## 8. Known Warnings (seen in the live test, harmless)

The restore was `Completed` but gave **10 warnings**. Inspected with `velero restore describe --details`:

```bash
POD=$(oc get pods -n openshift-adp -l app.kubernetes.io/name=velero -o jsonpath='{.items[0].metadata.name}')
oc exec -n openshift-adp "$POD" -c velero -- ./velero restore describe poc-oadp-demo-restore --details
```

All warnings fall into two categories:

1. **Cluster-scoped resources already exist** (`CustomResourceDefinition:clusterserviceversions.operators.coreos.com`, `SecurityContextConstraints:restricted-v2`) — these are shared cluster-wide resources and were not overwritten with the backup's version (**correct behavior**; otherwise it would affect the rest of the cluster).
2. **Auto-generated resources inside the namespace already exist** (the `pipeline-dockercfg-xxxxx` secret, the `istio-ca-crl`/`istio-ca-root-cert`/`kube-root-ca.crt`/`openshift-service-ca.crt` ConfigMaps, the `openshift-pipelines-edit`/`pipelines-scc-rolebinding` RoleBindings) — as soon as the namespace is recreated, OpenShift's own controllers (service account controller, CA injector, OpenShift Pipelines operator, etc.) **regenerate them automatically**; by the time the Velero restore runs they already exist, hence the "already exists" warning. **Not real data loss.**

**Practical takeaway:** seeing these warnings is normal and expected — what really needs checking is whether the resources **belonging to your application** (Deployment, ConfigMap, Secret, your own RoleBindings, etc.) came back with their content (verified in section 7).

## 9. Cleanup

> ⚠️ **Snapshot left behind by the restore:** while restoring the PVC, Velero creates a VolumeSnapshot/VolumeSnapshotContent with `deletionPolicy: Retain` in the namespace. Even after the namespace is deleted, this snapshot **stays in Ceph** (confirmed in the live test). Change its policy to `Delete` before deleting.
>
> Also, `oc delete backup.velero.io` deletes only the Kubernetes object; for the backup data in S3 and the CSI snapshots, use a **`DeleteBackupRequest`** (Velero also cleans up the restore records itself).

```bash
# Switch the Retain snapshots left by the restore to Delete
for c in $(oc get volumesnapshot -n poc-oadp-demo -o jsonpath='{.items[*].status.boundVolumeSnapshotContentName}'); do
  oc patch volumesnapshotcontent $c --type=merge -p '{"spec":{"deletionPolicy":"Delete"}}'
done
# Delete the backup together with its S3 data and snapshots
cat <<'EOF' | oc create -f -
apiVersion: velero.io/v1
kind: DeleteBackupRequest
metadata:
  generateName: poc-oadp-demo-backup-delete-
  namespace: openshift-adp
spec:
  backupName: poc-oadp-demo-backup
EOF
oc delete ns poc-oadp-demo
# If no other guide (17 — Virtualization) will use the DPA:
oc delete dpa dpa-odf -n openshift-adp
oc delete secret cloud-credentials -n openshift-adp
oc delete obc oadp-bucket-odf -n openshift-adp
```

## Summary

| Component | Namespace | Role |
|---|---|---|
| OADP Operator | `openshift-adp` | Manages Velero and the `DataProtectionApplication` CRD |
| `ObjectBucketClaim` (Ceph RGW) | `openshift-adp` | Provides the S3 bucket backups are written to |
| `DataProtectionApplication` (`dpa-odf`) | `openshift-adp` | Defines which S3 Velero writes to, with which credentials |
| `Backup` (`velero.io`) | `openshift-adp` | Backs up all Kubernetes resources of the given namespace to S3 |
| `Restore` (`velero.io`) | `openshift-adp` | Restores the namespace + resources from a backup |

**Golden rules:**
1. Always use **`oc get backup.velero.io`** instead of `oc get backup` — on this cluster there is a name collision with CloudNativePG's `backups` resource.
2. If NooBaa is unhealthy (see the [12 — Logging README](../12-logging/README.md)), switch to **Ceph RGW** — the same S3 backend logic applies to OADP.
3. "already exists" warnings on restore are mostly **harmless** — the real verification is checking that your own application resources came back **with their content** (ConfigMap/Secret data, replica count, etc.); don't rely only on `phase: Completed`.
4. PVC data was backed up and verified with **CSI snapshots** (section 5.1). File-level backup (`nodeAgent`/kopia, `defaultVolumesToFsBackup: true`) or copying the data to S3 (`snapshotMoveData`) can be enabled separately; they are off in this POC.
5. When cleaning up the `Retain` snapshots left by the restore and the backups in S3, use a `DeleteBackupRequest` (section 9).
